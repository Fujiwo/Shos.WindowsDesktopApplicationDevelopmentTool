# Windows デスクトップアプリの自律開発(windev)

## 前提: ここではビルドできないが、windev ならできる

このスキルは、Claude Code が WSL(Linux)で動いているときのためのものである。Windows の上で直接動いていて、Bash から Windows の `dotnet` や `MSBuild.exe` をそのまま使えるなら、このスキルは要らない(`uname` が `Linux` を返すか、`/mnt/c` があるかで分かる)。

WSL では、Linux の `dotnet` は WPF / WinForms / C++ をビルドできず、サンドボックスが有効なら `cmd.exe`、`powershell.exe`、`*.exe` も拒まれて失敗する。だが、MCP サーバー **windev** が Windows 側で動いていて、ビルド・テスト・アプリの起動と終了を引き受ける。だから「Windows でビルドしてください」と人に頼む理由はない。windev のツールで自分で確かめ、自分で直す。

人に頼むと、そのたびに自律のループが止まる。人に頼んでよいのは、末尾の「人に頼んでよい場面」に当たるときだけである。

## ツール

| ツール | 引数 | すること |
|--------|------|----------|
| `mcp__windev__build` | `project`、`configuration`(`Debug` / `Release`)、`platform`(省略可。`x64` / `Win32` / `x86` / `ARM64`) | C# は `dotnet build`、C++(`.vcxproj` と、それを含むソリューション)は Visual Studio の `MSBuild.exe` |
| `mcp__windev__test` | `project`、`filter`(省略可) | C# のプロジェクトかソリューションは `dotnet test`(ビルドもする)。C++ はビルド済みのテストの `.dll` を `vstest.console.exe` で実行(ビルドはしない) |
| `mcp__windev__run_app` | `app`(登録した名前)、`seconds`(観察の秒数) | アプリを起動し、観察した後に必ず終わらせる |

- `project` は、windev の作業フォルダー(`bridge.json` の `workspaceRoot`)からの相対パスを `/` 区切りで書く。絶対パス(`/mnt/c/...`、`C:\...`)と、作業フォルダーの外は断られる。作業フォルダーがリポジトリの親フォルダーのこともある。`ファイルがありません` と返ったら、リポジトリの名前を前に付けるなど、パスの起点を見直す。
- MCP の登録の名前が `windev` でなければ、ツールの名前は `mcp__<名前>__build` などになる。
- MCP のツールは、名前だけが見えて中身が読み込まれていない(遅延読み込み)ことがある。`mcp__windev__...` が呼べる形で見当たらなければ、まず ToolSearch で `windev` を探して読み込む。それでも無い、またはつながらないときだけ、自分で回避しようとせずに、[references/setup.md](references/setup.md) の内容をユーザーに伝えて止まる。

## 回し方

小さく変え、すぐ確かめる。テストは、修正の前に失敗することを見ておく(何も検証しないテストを見分けるため)。

**C#**

1. 編集する。
2. `test` でテストのプロジェクト(またはソリューション)を実行する。新しいテストは失敗するはず。
3. 直す。
4. `test` で、すべて成功するまで 3 と 4 を繰り返す。
5. 画面に関わる変更なら、`build` でアプリをビルドし、`run_app` で起動と終了を確かめる。

**C++ / MFC / Win32**

1. 編集する。
2. `build` でテストのプロジェクト(またはソリューション)をビルドする。`test` はビルドしないので、ビルドを飛ばすと古い DLL をテストしてしまう。
3. `test` に、ビルドしてできたテストの `.dll` を、作業フォルダーからの相対パスで渡す。DLL の場所は、ビルドの出力の `App.Tests.vcxproj -> C:\...\App.Tests.dll` の行で分かる。この行は Windows の絶対パスなので、作業フォルダーまでの部分を取り除き、`\` を `/` に直して渡す。
4. 直して、2〜3 を繰り返す。
5. 画面に関わる変更なら、アプリのプロジェクトを `build` してから `run_app`。

C++ のテストの DLL の場所は、ビルドの仕方で変わる。古い DLL をテストしないように、ビルドの起点(ソリューションか、プロジェクトか)を毎回そろえる。

| `.vcxproj` の `OutDir` | ソリューションからビルド | `.vcxproj` を単独でビルド |
|------------------------|--------------------------|---------------------------|
| 既定(`$(SolutionDir)$(Platform)\$(Configuration)\`) | ソリューションの隣の `x64/Debug/App.Tests.dll` | プロジェクトの隣の `x64/Debug/App.Tests.dll` |
| `$(MSBuildProjectDirectory)\bin\...` などに変えてある | どちらでも同じ(例: `tests/App.Tests/bin/x64/Debug/App.Tests.dll`) | 同左 |

C++ では `platform` を指定する。名前は、渡すものによって違う。

| 渡すもの | 64 ビット | 32 ビット | 省略したとき |
|----------|-----------|-----------|--------------|
| `.vcxproj` | `x64` | `Win32` | 多くは `Win32`。その構成が無いと `MSB8013` |
| `.sln` / `.slnx` | `x64` | `x86` | ソリューションの既定。ソリューションに `Win32` を渡すと `MSB4126` |

## 結果の読み方

- 先頭行は、`結果: 成功(終了コード 0)`、`結果: 失敗(終了コード n)`、`結果: 時間切れ(n 秒で止めました)` のどれかである。
- 失敗したら、標準出力の中から最初のエラーを探す。後のエラーは、最初のエラーの巻き添えのことが多い。

  | 印 | 出どころ |
  |----|----------|
  | `error CS....` | C# のコンパイラー |
  | `error C....` | C++ のコンパイラー |
  | `error LNK....` | C++ のリンカー(定義の不足、ライブラリの不足) |
  | `error MSB....`、`error NETSDK....`、`error NU....` | ビルドの定義、SDK、NuGet |
  | `Failed ...`、`Assert` | テストの失敗(期待値と実際の値が出る) |

- 出力は、標準出力と標準エラー出力のそれぞれ末尾 12,000 文字だけが返る(`(先頭の n 文字を省略)` と出る)。足りなければ、`filter` でテストを絞るか、プロジェクト単位でビルドする。
- 断られた要求は、理由付きのエラーで返る(`作業フォルダーの外は指定できません`、`登録されていないアプリです(登録済み: ...)` など)。理由に従って引数を直す。
- 文字コード: windev は UTF-8 と Shift-JIS(コードページ 932)を判定し、UTF-8 に揃えて返す。こちらで変換しない。それでも化けていたら、そのまま報告する。

よくあるエラーと直し方は [references/troubleshooting.md](references/troubleshooting.md) にある。

## GUI アプリ

アプリは `run_app` でだけ起動する。Bash や `start` で起動すると、終わらないプロセスが残って次のビルドの上書きを妨げ、ループが止まる。`run_app` は、観察の後に窓を閉じる要求を送り、5 秒で終わらなければ強制終了するので、ハングしても止まらない。

| 出力 | 意味 |
|------|------|
| `観察の後、ウィンドウを閉じて終了させました` と `メインウィンドウ: "<タイトル>"(応答あり)` | 正常に起動して閉じた |
| `観察のうちに自分で終了しました` | GUI のアプリなら、起動直後の異常終了を疑い、終了コードと標準エラー出力を読む(コンソールのアプリが終了コード 0 で終わったのなら正常) |
| `(応答なし)` | ハング。UI スレッドを止めている処理(同期の待ち、重い処理)を探す |
| `メインウィンドウ: なし` | 窓が出ていない。例外、起動の条件、窓の作成の失敗を疑う |
| `閉じる要求で終了しなかったので強制終了しました` | 閉じる処理(確認ダイアログ、終了時の待ち)を疑う |

`run_app` では画面の中身までは確かめられない。確かめたいロジックは画面から分けて、単体テストで確かめる。

## 書くときの注意

- ソースは BOM のない UTF-8 で書く。C++ のプロジェクトに `/utf-8` が無いと、日本語の Windows はソースをコードページ 932 として読み、C4819 の警告や文字化けが起きる。そのときは `.vcxproj` に `/utf-8` を足す編集を提案する。
- ビルドの定義(`*.csproj`、`*.vcxproj`、`*.props`、`*.targets`、`nuget.config`、`global.json`)の編集は、承認を求められることがある。ビルドのときに任意のコマンドを走らせられる場所なので、変える理由を一言添える。
- テストのプロジェクトが無ければ作ってよい。C# は `dotnet new xunit --no-restore` などで作る。作るだけなら Linux の `dotnet` でもよく、リストアとビルドは windev の `build` / `test` に任せる。サンドボックスではホームに書けず `dotnet new` が失敗することがあるので、そのときは `DOTNET_CLI_HOME` を `$TMPDIR` の下に向けてやり直す。WPF / WinForms のプロジェクトを参照するなら、`TargetFramework` をアプリと同じ `net*-windows` にする。C++ は `<ProjectSubType>NativeUnitTestProject</ProjectSubType>` を付けた DLL にする。どちらもソリューションに足す。

## してはいけないこと(と、その理由)

- Bash で `dotnet build` / `dotnet test` / `dotnet run` / `msbuild` / `cmd.exe` / `powershell.exe` / `*.exe` を呼ばない。理由は二つある。一つは、サンドボックスで失敗するか、Linux の `dotnet` で Windows 向けのビルドが失敗して、原因を取り違えること。もう一つは、Windows でできる操作を windev の 3 つのツールに絞ること自体が、ホストを守る境界であること。サンドボックスが無い環境で Windows のコマンドが動いても、境界の外に出ることになる。
- `bridge.json`、ブリッジの実行ファイル(`C:\Tools\WinDevBridge` など)、MCP の登録、`.claude/settings.json` を変えようとしない。これらは安全の境界で、ユーザーが管理する。
- サンドボックスを外す、`dangerouslyDisableSandbox` を使う、Interop を開くといった回避をしない。

## 人に頼んでよい場面

次のどれかに当たったときだけ止まり、ユーザーに頼む。

- windev のツールが無い、つながらない(`/mcp` で確かめてもらう)。
- `bridge.json` を変える必要がある(アプリの登録、作業フォルダー、時間切れの延長、MSBuild の版の固定など)。
- Visual Studio のコンポーネントが足りない(`Visual Studio が見つかりません`、`MSB8020` のツールセットの不足、MFC のライブラリの不足、Windows SDK の不足)。
- 権限で拒まれた操作が、作業にどうしても要る。

頼むときは、次の 3 点を書く。

1. 何をしようとしたか。
2. どのツールに何を渡し、何が返ったか(エラーの全文)。
3. ユーザーにしてほしいこと。具体的に書く(例: 「`bridge.json` の `apps` に `"App": "src/App/bin/x64/Debug/App.exe"` を足して、Claude Code を起動し直してください」)。
