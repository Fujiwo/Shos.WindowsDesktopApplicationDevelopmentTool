# よくあるエラーと直し方

windev のツールの結果で、原因の見当が付かないときに読む。まず自分で直せるものかを見分け、直せないもの(「ユーザーへ」)だけを人に頼む。

## windev が断った要求

| メッセージ | 直し方 |
|------------|--------|
| `作業フォルダーからの相対パスで指定してください` | `/mnt/c/...` や `C:\...` を、`workspaceRoot` からの相対パスに直す |
| `作業フォルダーの外は指定できません` | `..` で外に出ていないか見直す。リポジトリが作業フォルダーの外にあるなら、ユーザーへ(`workspaceRoot` の変更) |
| `ファイルがありません` | パスの起点を見直す(作業フォルダーがリポジトリの親のこともある)。C++ のテストの DLL なら、先に `build` したか、ビルドの出力の `-> ...dll` の行のパスを相対パスに直したか、ソリューションとプロジェクトのどちらからビルドしたか(既定の `OutDir` では場所が変わる)を見る |
| `プロジェクトかソリューション(...)を指定してください` | `.csproj` / `.vcxproj` / `.sln` / `.slnx` を渡す |
| `テストのプロジェクトかソリューション、または C++ のテストのビルドした DLL(...)` | C++ のテストに `.vcxproj` を渡した。`build` してから、できた `.dll` を渡す |
| `構成は Debug か Release を指定してください` / `プラットフォームは ... のどれか` | 一覧の値を使う。`Any CPU` は渡せないので、省略する |
| `登録されていないアプリです(登録済み: ...)` | 登録済みの名前を使う。無ければユーザーへ(`apps` への登録) |
| `観察する秒数は 1〜n 秒で指定してください` | 範囲の中の秒数にする |
| `C++ のワークロード ... の入った Visual Studio が見つかりません` | ユーザーへ(Visual Studio のコンポーネントの追加、または `msbuildPath` / `vstestPath`) |

## ビルド

| 症状 | 原因と直し方 |
|------|--------------|
| `MSB3027` / `MSB3021`(ファイルをコピーできない)、`being used by another process` | 前に起動したアプリや、テストのプロセスが残っている。または同期のソフトがファイルを握っている。もう一度 `build` する。2 回続けて同じなら、ユーザーへ(握っているプロセスや同期の確認) |
| `MSB8020`(ツールセット `v14x` のビルド ツールが見つからない) | プロジェクトのツールセットが入っていない。`PlatformToolset` を変えるのはビルドの定義の変更なので、勝手に変えずにユーザーへ(ツールセットの追加、`msbuildPath` での版の固定、または変更の承認) |
| `MSB8036`(Windows SDK が見つからない) | `WindowsTargetPlatformVersion` を `10.0`(入っている最新)にするか、ユーザーへ(SDK の追加) |
| `MSB8013`(プロジェクトに、その構成とプラットフォームの組が無い) | `.vcxproj` に `platform` を指定する(多くは `x64`。32 ビットは `Win32`) |
| `MSB4126`(ソリューションの構成が無効) | ソリューションに渡すプラットフォームの名前を直す(32 ビットは `Win32` ではなく `x86`)。分からなければ `.sln` / `.slnx` の中の構成の一覧を読む |
| `C1083`(インクルードファイルを開けない) | インクルードのパスかファイル名の誤り。MFC の `afxwin.h` なら、MFC のコンポーネントが無い → ユーザーへ |
| `LNK2019` / `LNK2001`(未解決の外部シンボル) | 定義が無い、`.cpp` がプロジェクトに入っていない、ライブラリが足りない。`.vcxproj` の `ClCompile` を見る |
| `C4819`、日本語の文字化け | ソースが UTF-8 なのにコードページ 932 で読まれている。`/utf-8` を足す |
| `NETSDK1100`(Windows 向けのビルドに `EnableWindowsTargeting` が要る) | Linux の `dotnet` で呼んでいる。windev の `build` を使う |
| `NU1301`(パッケージのソースに届かない) | Windows 側のネットワークか NuGet の設定。ユーザーへ |

## テスト

| 症状 | 原因と直し方 |
|------|--------------|
| `No test is available` / テストが 0 件 | C#: テストのフレームワークとアダプターのパッケージが入っているか。C++: DLL が古い(`build` を忘れた)、`NativeUnitTestProject` でない、`filter` が合っていない |
| テストの DLL を読めない(プラットフォームの食い違い) | x64 の DLL を x86 のホストで読もうとしている。ユーザーへ伝え、`vstestPath` の版やブリッジの更新を相談する |
| `時間切れ` | 待ち続けるテスト(GUI を出す、ネットワークを待つ、デッドロック)がある。`filter` で絞って特定する |

## アプリの起動(run_app)

| 症状 | 原因と直し方 |
|------|--------------|
| `ファイルがありません`(登録したアプリ) | アプリをまだビルドしていないか、出力の場所が登録と違う。`build` してからもう一度。場所が違うならユーザーへ |
| すぐ終了し、終了コードが `-532462766`(0xE0434352) | .NET の未処理の例外。標準エラー出力のスタックトレースを読む |
| すぐ終了し、終了コードが `-1073741515`(0xC0000135) | DLL が見つからない(C++ の実行時ライブラリ、依存の DLL)。出力のフォルダーに要る DLL があるかを見る |
